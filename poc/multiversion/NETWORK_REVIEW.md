# Отдельная оценка потоков и сети текущего SDK

Дата: 2026-10-15. Статический разбор исходного `fte-api`, без изменений его кода.
Это не результаты runtime-проверок сетевого SDK и не часть реализации PoC.
PoC вообще не использует ApiClient, RelayClient, SSE или существующие трекеры.

Это историческое состояние первого этапа. После подтверждения паритета 4B
исправления реализованы отдельно в 4C; фактические тесты и пределы гарантий
описаны в [PHASE4_RESULTS.md](PHASE4_RESULTS.md). Наблюдения ниже сохранены
как исходный список проблем release SDK.

## Подтверждённые свойства кода и их последствия

| Участок | Наблюдение | Последствие / отдельная будущая работа |
| --- | --- | --- |
| `ApiClient.postJson`, `postJsonForResponse`, `buildPostRequest` | Gson и gzip выполняются до `HttpClient.sendAsync` | Сеть асинхронна, но сериализация и сжатие остаются на вызывающем потоке. При вызове трекером это работа клиентского потока. Нужен отдельный ограниченный исполнитель подготовки запросов. |
| `RelayClient.sendMessage` | Сериализация уже вынесена в single-thread executor | Полезное существующее поведение; переписывать transport ради самого PoC не требуется. |
| `RelayClient.pending` и executor | ConcurrentLinkedQueue и стандартная очередь single-thread executor не имеют заданного лимита | При продолжительной недоступности backend возможен рост памяти. Для наблюдений нужна ограниченная очередь/coalescing, для событий — отдельная TTL-политика. |
| `RelayClient.sendRaw` | `webSocket` читается при проверке и повторно при вызове; флаг auth отдельный | `volatile` не делает составную операцию атомарной. Соединение может смениться/обнулиться между чтениями. Нужен захват состояния соединения и проверка его поколения. |
| `RelayClient` callbacks | onClose/onError/watchdog меняют глобальные поля без проверки, что callback относится к текущему соединению | Поздний callback предыдущего соединения потенциально затронет новое. Требуется отдельная проверка этого сценария. |
| `RelayClient.flushPending`, `sendRaw` | Flush выполняется из callback, sendMessage — из IO executor; результаты sendText не обрабатываются | Нужны последовательный send pipeline и обработка CompletionStage, включая отказ и обрыв. Не следует обещать exactly-once без idempotency на backend. |
| `RelayClient` auth timeout | Возврат из doConnect при таймауте сам по себе не закрывает созданный WebSocket | Проверить очистку неаутентифицированного соединения до следующей попытки. |
| `SseCache.readStream` | Во всех повторных попытках используется тот же переданный CompletableFuture ответа | Это не фабрика новых SSE-запросов: после EOF/ошибки будет повторно использован прежний response/stream. Нужен supplier нового запроса для каждой попытки. |
| `SseCache.stop` | Флаг + interrupt; активный InputStream не хранится для явного закрытия | Нельзя считать гарантированным прерыванием блокирующего readLine. Хранить/закрывать поток и отменять запрос при остановке. |
| `RelayCache`, `SseCache` | Очистка ConcurrentHashMap и последовательное заполнение | Нет атомарного снимка; читатель может увидеть пустой/частичный результат. Публиковать целостное состояние одной ссылкой. Это обновление по сетевому событию, а не аллокации снимка мира каждый тик. |
| `FunTimeEventsAPI.create` | Повторный Builder возвращает singleton и игнорирует конфигурацию | Не создаёт вторые трекеры, но не поддерживает независимые API-ключи двух consumer-модов. Нужна явная продуктовая политика. |
| `FunTimeEventsAPI.create` offline | `sender` остаётся null; трекеры могут вызвать sender.send... | Offline mode нужно отдельно проверить и заменить null безопасным sender, не добавляя сетевую отправку. |
| `Bootstrap.start` | started выставлен до завершения проверки/регистрации | Возможна частично завершённая инициализация; нужна атомарная публикация готового runtime и откат ресурсов при ошибке. |
| `Bootstrap.onWorldLeave` | Останавливаются scheduler и trackers, но не backend-транспорты | Не обязательно ошибка: глобальные GET могут работать в меню. Нужно явно разделить SDK lifetime и игровую сессию; остановка клиента должна закрывать ресурсы. |
| `Scheduler` | Проверки running/task и task.run раздельные | Безопасность зависит от одного потока-владельца. Если stop разрешён конкурентно, volatile недостаточно. |
| Локальные кеши | Donate-кеши живут дольше одной игровой сессии, DungeonTracker.stop их не очищает | Сбросить игровые кеши при смене сервера; не путать их с глобальными данными backend. |

## Предлагаемая модель владения, без её реализации

1. Minecraft и состояние трекеров принадлежат клиентскому потоку.
2. Сеть получает уже сформированные данные с зафиксированным server context и generation игровой сессии.
3. Сериализация/сжатие и отправка выполняются вне клиентского потока с ограничением очередей.
4. Состояние соединения принадлежит последовательному transport pipeline; callbacks старого поколения не меняют новое соединение.
5. Публичные кеши публикуются как целостные состояния; mutable DTO потребителю не дают права менять внутренний кеш.
6. `volatile` применяется для публикации между потоками, но не заменяет ownership, locks или атомарные переходы.

## Почему это оставлено отдельно

Проверка multi-project, namespaces, Maven и jar-in-jar не доказывает исправность
старого transport. Эти изменения следует выполнять отдельными патчами с локальным
HTTP/WSS/SSE backend и сценариями таймаутов, reconnect, EOF, shutdown и смены мира.
Существующие REST/WSS/SSE payload, интервалы и правила трекеров в PoC не менялись.
