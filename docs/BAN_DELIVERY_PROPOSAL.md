# Предложение backend: надёжная доставка BanPayload

Статус: **OPEN — требуется согласование SDK и FunTimeEventsAPI backend**.
Это предложение, а не реализованный протокол rc.2. Текущие JSON, HTTP headers,
WebSocket auth/snapshots и SSE не изменены. Новых retries, ACK и полей нет.

## Текущие категории

| Данные | Семантика | Доставка rc.2 |
|---|---|---|
| BanPayload | Историческое событие: наблюдение бана не отменяется выходом с сервера | Bounded FIFO, best effort; возможна потеря при TTL, overflow, shutdown, смене сессии или сбое сети |
| Координаты события | Наблюдение с ограниченным сроком актуальности | Тот же FIFO/TTL, но потерявшую актуальность координату нельзя бесконечно переотправлять |
| TAB/игроки, шахты, данжи, HellMap | Заменяемое текущее состояние | Coalescing по type/server, latest wins; устаревший snapshot заменяется или отбрасывается |

Нынешние ограничения: snapshots — 64 ключа/15 секунд; FIFO events — 256/30 секунд;
при переполнении FIFO отклоняется новое событие. Shutdown очищает очередь, смена
игровой сессии инвалидирует старые игровые payload. RC.2 сохраняет это поведение.
Завершение HTTP/WS send не является подтверждением сохранения события backend.
Потеря BanPayload при reconnect сейчас возможна; обещания at-least-once нет.

## Предлагаемый согласованный протокол vNext

1. SDK создаёт устойчивый `event_id` один раз при обнаружении бана (например, UUID).
   Повторная отправка сохраняет ID и исходный payload. ID в envelope, а не новая
   семантика существующих полей. Точное имя, версия envelope и capability negotiation
   должны согласовываться; старый backend по умолчанию получает старый JSON.
2. Backend выполняет idempotent insert с уникальным ключом `(principal, event_id)`
   в одной транзакции с сохранением события. После commit возвращает ACK с ID.
   Повтор с тем же ID и тем же содержимым возвращает тот же успешный ACK. Тот же ID
   с другим содержимым — явная ошибка, без перезаписи. Нельзя ACK до commit.
3. REST: согласованный ACK body после сохранения. WebSocket: отдельное сообщение
   `event_ack`; auth/connection ready не ACK события. Закрытие после commit до ACK
   оставляет результат неизвестным: SDK повторяет тот же ID, backend дедуплицирует.
4. SDK хранит bounded outbox до ACK/истечения retention. По умолчанию proposal:
   до 256 событий и 24 часов, лимит байтов дополнительно; backoff 1/2/4/8/… секунд
   с jitter, максимум 60 секунд. Это стартовые значения для обсуждения нагрузки,
   не утверждённая гарантия. 401/403 останавливают отправку до смены credentials;
   400/422 с terminal reject снимают событие с явной диагностикой; 429 учитывает
   Retry-After. Количество попыток ограничено retention и общим бюджетом.
5. При reconnect SDK сначала завершает auth и проверяет capability, затем отправляет
   pending события с исходными ID. Отправки последовательные/ограниченные; новый
   connection generation не принимает ACK от старого соединения. ACK сверяется
   с principal/ID и поколением транспорта, а не с текущей игровой сессией.
6. Bans outbox отделяется от session-fenced snapshots. Событие хранит исходный server
   ID; reconnect не подменяет его новым сервером. При смене API key/backend outbox
   нельзя молча передавать новому получателю. Нужна явная политика удаления либо
   отдельного хранения по прежнему principal/base URL.
7. Backend retention дедупликации должен быть дольше SDK retry/retention плюс допустимый
   clock skew и окно восстановления backup. Предложение: не менее 7 суток при SDK
   retention 24 часа. Удаление dedupe-записи раньше последнего допустимого retry
   снова допускает дубликат. Повторное наблюдение одного бана двумя клиентами будет
   иметь разные event_id: межклиентская дедупликация — отдельное backend-решение.

## Перезапуск и хранение

In-memory outbox не переживёт process crash/shutdown. Если backend требует доставки
после перезапуска, нужны согласованные durable outbox и политика персональных
данных: место хранения, атомарные записи/fsync, предел диска, очистка, права доступа,
привязка к principal без сохранения API key, запрет отправки после смены ключа.
Без этого даже утверждённый ACK-протокол обеспечит только ограниченные повторы в
рамках живого процесса. Persistent outbox не следует включать молча.

Overflow нельзя скрывать: счётчики dropped/expired/rejected и причина, без секретов.
Можно временно отклонять новое событие, сохраняя старые, либо удалять самое старое;
нужно выбрать продуктовую политику. Не блокировать Minecraft client thread.

## Координаты и snapshots

Координатам нужен отдельно согласованный observed_at/expires_at или TTL: retry после
истечения актуальности запрещён. Это не архив банов. Срок зависит от типа игрового
события и backend-очистки; текущий 30-секундный TTL остаётся до согласования.
Snapshots отправляют только последнее состояние текущей сессии: не восстанавливать
устаревшие TAB/игроков после reconnect и не смешивать их с исторической outbox.

## Одновременные изменения и проверки

| SDK | Backend |
|---|---|
| Capability negotiation, envelope/ID, bounded outbox, ACK correlation | Поддержка версии протокола и отдельного event ACK |
| Retry/backoff/retention и явные terminal errors | Транзакционное сохранение + unique constraint + одинаковый повторный ACK |
| Разделение historical/session-fenced данных | Срок dedupe retention, исходный server ID, правила credentials |
| Метрики drop/expired/ACK latency без секретов | Диагностика конфликтов ID, перегрузки и rate limit |

Обязательные тесты: commit-before-disconnect-without-ACK; duplicate REST/WS;
out-of-order/late ACK; reconnect/auth timeout; ID с другим payload; overflow/expiry;
429/backoff; смена ключа; process restart при принятом durable outbox; межклиентские
дубли. Проверять отсутствие двойного insert, а не только успешный send.

## Вопросы для согласования

1. Допустима ли потеря наблюдений о банах при reconnect/shutdown/process crash?
   Какое максимальное окно хранения и задержки приемлемо?
2. Будет ли backend поддерживать idempotent commit и ACK для REST и WS одновременно?
   Каковы scope ID, terminal error codes и retention dedupe?
3. Требуется ли дедупликация одного бана, независимо замеченного разными клиентами?
4. Допустимо ли локальное постоянное хранение исторических payload и на какой срок?
5. Какая политика overflow и смены API key/backend приемлема?

Без ответов безопасный вариант по умолчанию — сохранить текущий bounded best effort,
явно документировать возможную потерю и не вводить несовместимые поля/retries.
Даже с ACK/idempotency нельзя обещать exactly-once transport delivery; можно обсуждать
at-least-once попытки в согласованном окне и одно применение на backend при сохранённом
dedupe key. Эти гарантии потребуют совместных тестов и отдельного решения о протоколе.
